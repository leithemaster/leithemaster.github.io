The problem

An internal web platform for Marine support teams, built so support requests are easier to raise, follow and close. The original planning was finished before I joined. I came on midway and ended up the only designer on the project.

The design

I kept most of the original design and built on it. My focus was quality of life: making each task as easy as possible for the people doing it, instead of redoing the look.

I planned each feature as a user journey. The journeys let me show my PM why I made each decision, and they gave stakeholders something concrete to react to in feedback sessions.

The handoff

Every screen was reviewed against Section 508. I made the application usable by someone who is blind and added controller navigation, which matters on a military project where users may have impairments.

I wrote the user guide, using a workflow I set up for myself to make that faster. I also worked with the Angular developers on HTML/CSS layout and component styling during handoff.

The outcome

A portal that is easier to use day to day, accessible to users with visual and motor impairments, and documented with a user guide.

The problem

The utility had products to show and training to offer, and no single place for either. The portal was meant to be that place: a product showcase and a training hub for base traffic control.

The design

I designed the portal in Adobe XD. The design itself was straightforward. The harder part was stakeholder communication. The person in charge was a manager rather than a PM, and she decided best by comparing options. For simple decisions I would produce several designs so she could pick one.

The build

As the only designer and web developer, I took the portal from first layout to the finished build myself, so there was no handoff to lose detail in.

The outcome

A working portal that brings the utility's products and training together. Working through design decisions with a stakeholder who needed to see options first built my people skills, and I still use them when I work with stakeholders.

The problem

NexGen is an internal web application at USCIS. The work was new features, built across the full stack.

The design

I was hired to build, and I also had a hand in the design. I owned the theming and made mockups with the senior designer and my peer, and I gave feedback on design changes. I joined design review sessions, kept UX feedback loops running between design and development, and took part in Agile sprint planning.

My approach was to improve the existing application instead of remaking it. I based my choices on feedback and survey questions from the workers who use it, so core features would be easier to use and faster to get through. The client told me directly that most of my designs were great and easy to understand.

The build

Frontend, React. UI components, feature enhancements and hook-based logic.

Backend, Spring. API integration, PostgreSQL queries and business-logic updates.

The outcome

New features shipped across the stack, from React components and hooks down to Spring Boot logic and PostgreSQL queries, with the usability and performance of core features improved along the way.

04

A mobile-first game, coded by me with help from AI

Client
Independent
Years
2026–now
Role
Programmer and designer, team of two
The brief
An incremental game for a big online platform where most players are on a phone: collect, cash in, upgrade, and watch the numbers climb, from bare hands to a vacuum that works like a black hole. It has to hook a player in seconds and run smoothly on a mid-range phone.
My part
I write the design doc, design the UI and card art in Figma and bring it into the game, and code the game in Lua, with Claude Code helping along the way. My partner funds the game, runs the playtests and has the final say.
The result so far
The core loop, the world, ball physics, 39 collectible items and a 47-icon set are built and in the game. Shops and UI polish are in progress. It hasn't launched, so there are no player numbers yet.
Read the full case studyClose the case study ↳

The problem

Players on game platforms decide in seconds, and most of them are on a phone. The game had to give a first reward within 15 seconds, stay smooth on a mid-range phone, and be safe for an audience that includes players under 12. I came in strong in TypeScript and new to Lua and game engines.

The design

I prototyped the core action first, picking up balls, to check it was fun on its own before designing around it. Then I wrote the design doc and its pillars: one action with an instant payoff, visible progress, and performance first. A feature that drops frames on a phone gets cut back, however good it looks.

We designed the interface in Figma first: the HUD, the menus, the shop cards and a 47-icon set, reviewed in rounds and then brought into the game. That was the most fun part, seeing a card go from a Figma frame to something a player taps. The UX rules came from my design background. The first five minutes show one currency and one action. Menus use a single book-style window, with odds and bonuses on the cards instead of in text lists. Tap targets are at least 44 points, text contrast is at least 4.5:1, nothing relies on colour alone, and a setting turns off motion and flashing. Spending stays honest: odds are shown and there are no dark patterns.

The build

I write the code in Lua, with Claude Code connected into the game engine through MCP as a helper. On bigger changes I write the spec and let it draft, then review every line before it stays. When the AI ran into its limits, I wrote the code myself. After every script edit there's a playtest, the console has to be clean, and changes that touch data are tested against a fresh save.

The project runs like a small studio. The design doc tags every decision with who made it, tasks and playtests are GitHub issues, and the build moves in phases that each end with a phone performance check. A Python pacing model tunes the economy to four or five hours of play.

The outcome

The core loop, the world, ball physics, 39 collectible items and a 47-icon set are in the game, with a HUD that works on PC and touch. Shops and UI polish are next, then launch. What I've learned so far is how to work with AI on a real project: clear specs, small steps, a review of every change, and knowing when to just write the code myself.
